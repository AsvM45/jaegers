# JAEGERS | Repository guardrails
- Public monorepo: `Jaeger_Main/House_Edge/` and `Jaeger_Main/Hitachi/` are separate. Work only in the requested subtree. Do not alter Hitachi when solving House Edge.
- At the start of a substantive task inspect `git status --short`, branch, HEAD and relevant files; preserve teammate modifications. The public remote may be behind/ahead of the local working tree.
- Scope changes narrowly, run real checks, and report observed commands/results; never invent scores, tests, acceptance or hidden labels.
- An agent may implement/test in its specifically claimed isolated worktree. When its issue-level permission allows, it may commit/push its own named feature branch and open a draft PR for human review; **never** push directly to main, merge PRs, overwrite a submission, upload to organizers, publish secrets, use paid cloud or perform irreversible actions without explicit human authorization. Plan-mode tasks are read-only.
- Store no secrets, credentials, hidden evaluation outputs or private information in Git. Avoid committing generated runs or unreviewed external assets.
- For House Edge, start Codex in `Jaeger_Main/House_Edge/`; obey its nested `AGENTS.md`. Use skills only when their descriptions match the task. Long docs are reference, not mandatory reading for every edit.

- Shared agent infrastructure: Codex, Claude Code and Google Antigravity use these repository guardrails. Antigravity natively reads these `AGENTS.md` files and shared `.agents/skills/`; see `docs/ANTIGRAVITY_START.md` and `.agents/rules/antigravity-coordination.md` for its scoped lane.
- Multi-agent ownership is tracked in `docs/MULTI_AGENT_OWNERSHIP.md` and GitHub issue #18. Never have two coding agents edit the same working tree. A human-approved separate worktree/branch and an explicit file scope are required for parallel implementation.

Grok is reserved for separate advanced temporal/statistical issue #15 pending a named claim; #9 is claimed by Claude Code with PR #28; Cursor is already claimed on CI #16. - One **implementing agent** per issue, one active editing issue per agent, one independent worktree per editor, and explicit writable-file boundary. Latest issue claim/handoff outranks a default owner table. A GitHub assignee can be a shared account and is not a live agent identifier.
- Behave as an accountable engineer: inspect, implement, test, debug, self-review, document actual evidence, open issue-linked review PR when authorized. Do not stop at a plan or invent ongoing/background execution.
- GitHub is the shared working memory: `docs/` canonical vetted knowledge; Issues claims/tasks; PRs integration; Projects dashboard; Discussions open hypotheses when enabled; Actions CI; Wiki a reviewed public docs mirror. See `docs/GITHUB_OPERATING_SYSTEM.md`. No raw private Library/chat archive in public GitHub.

- **Mandatory team-collaboration policy:** Before editing, read `docs/AGENT_COLLABORATION_PROTOCOL.md` and issue #18. Every concurrently coding agent requires its own physical Git worktree/clone AND unique `agent/...` or `human/...` branch, a named claimed issue and exclusive file-write scope. Communicate interface contracts, blockers and reviews like human teammates. Use issue-linked PRs; no self-merging, direct main pushes or silent handoffs. Shared GitHub assignees do not establish AI agent identity.
